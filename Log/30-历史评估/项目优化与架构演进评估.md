# WhisperSubtitle 项目优化与架构演进评估

> 仅记录从仓库中取得的事实与基于事实的分析。

## 初始状态

- 工作区已有用户改动：`.claude/settings.local.json`，本轮不触碰。
- 项目是 Windows 上的 Python/PyQt Whisper 字幕工具；源码集中于 `src/gui`、`src/core`、`src/utils`。
- 仓库只有一个初始化提交；没有可见的 CI、正式测试目录、Python 包配置或 README。
- 根目录包含完整虚拟环境 `whisper_env`，但被 `rg --files` 默认清单排除/忽略；仍需检查 `.gitignore` 是否妥善处理。
- `src/core` 同时保留四个相近版本：`WhisperProject.py`、`WhisperProject2.py`、`WhisperProjectCN.py`、`WhisperProjectCN2.py`，存在重复实现和演进分叉风险。
- `docs/architecture` 已有一套架构诊断资料，需要与实际代码交叉验证，不能直接视作结论。
- 启动方式包含 `launch.vbs` 和 Windows 快捷方式，明显偏向单机 Windows 环境。

## 第一轮代码盘点

- GUI 文件 `src/gui/WhisperPyQtGUI.py` 为 1132 行单文件，混合了界面构建、样式、文件选择、进程控制、性能监控、日志、环境检查与配置展示。
- 四个核心脚本约 281–329 行，各自包含完整 CLI、模型加载、文件遍历、推理、文本后处理和写盘流程；共同流程没有被抽取。
- `requirements.txt` 固定了约 80 个直接和间接依赖，并包含 PyTorch/CUDA nightly 版本；这更像 `pip freeze` 快照，不是可维护的顶层依赖声明。
- `launch.vbs` 将项目内虚拟环境、环境自检、错误临时文件和 GUI 启动绑死在一起；适用于当前机器，但不利于安装、升级和跨环境调试。
- `.gitignore` 已忽略 `whisper_env/` 与 `models/`，大文件未进入当前 Git 清单，这是合理的；但项目没有提供模型获取与环境复现说明。
- GUI 当前通过 `QProcess` 启动不同核心脚本，进程隔离有利于避免 UI 卡死，但以“脚本文件名”充当业务接口，会让后续重构、参数校验和测试变困难。
- 现有文档已经指出模型每次任务约有 5.3 秒加载成本、路径硬编码、配置双份维护、无设置持久化等问题；需继续以当前代码行号验证。

## 可量化的耦合与缺陷

- 四个核心脚本两两文本相似度约 0.697–0.846；它们不是四套独立业务，而是同一流水线的高重复变体。
- `txt_to_md` 在四个脚本完全重复；英文大小写/标点函数在两个英文脚本重复；中文标点和分段合并在两个中文脚本重复。
- GUI 主类 `WhisperMinimalGUI` 占 955 行，其中 `_build_ui` 单方法 503 行；这是后续维护和模块测试的首要热点。
- `src/core/presets.py` 已经把四种模式的推理参数集中为单一数据源，这是很好的模块化起点；后续应把 `script` 字段替换成策略/处理管线 ID，而不是继续绑定物理脚本名。
- 明确缺陷：`PRESETS` 包含 `cn2 -> WhisperProjectCN2.py`，但 `src/utils/test_env.py` 的 `CORE_SCRIPTS` 只检查前三个脚本，启动自检无法发现 CN2 脚本缺失。
- 环境自检刻意不检查 `torch`、`faster_whisper`、CUDA 和模型完整性，因此“启动检查通过”只表示 GUI 和若干路径存在，不表示转录真正可用；产品文案应区分轻量检查与推理就绪检查。
- GUI 混用 PyQt5 与 tkinter 文件选择框，产生双 GUI 工具包依赖、主题/高 DPI/焦点行为不一致，也增加打包复杂度；应统一为 `QFileDialog`。
- 性能监控处多次使用静默 `except Exception: pass`，会把驱动/NVML 初始化与运行问题完全隐藏，降低可诊断性。
- GUI 的 `closeEvent` 没有停止仍在运行的 `QProcess`；关闭窗口时子进程的生命周期和输出完整性缺乏明确保障。
- “停止”操作在 GUI 主线程调用 `waitForFinished(5000)`，窗口最多会冻结 5 秒；应改为 `terminate` 后通过定时器异步升级为 `kill`。
- 工程没有标准 Python 包结构（无 `pyproject.toml`、包级 `__init__.py`），GUI 通过修改 `sys.path` 导入 `presets`；这会妨碍模块化、测试、打包和 IDE 类型分析。
- 跟踪文件里存在 `.workbuddy/tmp/fix_prefix.py`、本机 `.claude/settings.local.json` 和历史 memory，说明仓库边界尚未整理；这些个人工具状态不应与产品源码混在同一发布边界。

## 冒烟测试结果

- `src/utils/test_env.py` 在当前环境通过，耗时约 127 ms；这验证的是轻量启动条件。
- 四个核心脚本 `--help` 均成功，但每次仅显示帮助就需约 1.36–1.80 秒，原因是参数解析前已导入 `faster_whisper`；CLI 初始化次序可优化。
- PyQt 离屏实例化成功：4 个 preset 均建立，`QProcess` 初始状态正常；说明当前 GUI 至少可完成构造。
- `pip show` 证明 `faster-whisper 1.2.1` 不依赖 PyTorch；项目中的 `torch` 只被核心脚本用于 CUDA 探测与设备信息。因此可用 `ctranslate2`/NVML 探测替代，移除 torch、torchaudio、torchvision 及其大批传递依赖（需先做真实转录回归）。
- `funasr` 与 `ttkbootstrap` 未被当前源码导入，像是旧实现残留；应从运行依赖中剥离或放入可选依赖组。
- 新发现的 CLI 兼容性缺陷：核心脚本直接在中文 Windows/GBK 控制台输出 emoji 时会触发 `UnicodeEncodeError`。GUI 子进程显式设置 UTF-8，所以从 GUI 启动通常不暴露；但文档给出的命令行直接调用不可靠。

## 关键正确性问题（按优先级）

### P0：模块化前必须修复

1. GUI 文件过滤器宣称支持 MP3/WAV/M4A/AAC/OGG，但四个 core 仅接受视频扩展名；模拟测试确认 WAV 会被拒绝。
2. core 在校验输入路径/扩展名之前加载模型；模拟测试确认无效 WAV 也先发生 `model_init`，真实环境会白费约 5 秒并占用显存。
3. 单文件处理异常被循环捕获后，`main()` 仍正常返回；模拟测试确认 0/1 成功时返回 `None`，作为进程运行即退出码 0，GUI 会误报“转录全部完成”。
4. CLI 默认 Windows GBK 输出无法编码日志中的 emoji，直接命令行使用可能崩溃。
5. `test_env.py` 没有检查 `WhisperProjectCN2.py`。
6. GUI 停止操作最多阻塞主线程 5 秒；关闭窗口也未显式处理仍运行的子进程。

### P1：高收益工程优化

1. 先验证输入和输出冲突，再加载模型；批量输入同名文件写到统一 `-o` 目录时需要明确冲突策略，建议保留相对目录或生成稳定唯一名，并采用临时文件 + 原子替换。
2. 将 `requirements.txt` 从虚拟环境快照改为顶层运行依赖；当前虚拟环境约 5.04 GiB，其中 `torch` 目录约 4.13 GiB。移除仅用于设备探测的 torch 系列，理论上可显著减小体积，但必须用真实 GPU 转录回归验证。
3. 将运行、开发、可选引擎依赖分组；清除当前未使用的 FunASR、ttkbootstrap 等残留。
4. 建立 `pyproject.toml` 和正式包结构，移除 `sys.path.insert`；提供一个 CLI 入口，而不是四个可执行脚本。
5. 统一使用 Qt 的 `QFileDialog`，加入 `QSettings`；用结构化日志替代全局 warning 屏蔽和静默异常。
6. 增加 README、安装/模型获取说明、最小 CI，以及不依赖模型的快速测试套件。

## 推荐的模块化目标

```text
Qt UI / Web UI / CLI（适配层）
                │
                ▼
TranscriptionService（提交、取消、进度、结果）
                │
                ▼
统一 Pipeline：发现媒体 → 推理 → 后处理 → 写出
        │                          │
        ▼                          ▼
WhisperEngine 接口          OutputWriter 接口
        │                          │
faster-whisper 适配器       本地文件适配器
```

- 四个 core 脚本应变成“一个管线 + 四个 preset + 可组合 postprocessor”，而不是继续复制完整流程。
- 建议保留进程隔离，但把脚本边界升级为稳定 worker：worker 独占模型，UI 通过 JSON Lines 或同等明确协议收发 typed event。这样可避免 UI 卡死，并能在多次任务间复用模型。
- `TranscriptionRequest`、`TranscriptionResult`、`ProgressEvent`、`Preset` 应是与 PyQt/faster-whisper 无关的普通 Python 数据对象。
- UI 只负责收集输入、展示状态和发送取消；它不应知道模型路径、CUDA、文件扫描、输出命名或具体脚本名。

## 分阶段路线

1. **基线与修错**：为后处理、preset、媒体扫描、退出码加测试；修复全部 P0；记录启动、模型加载、单段转录、峰值内存/显存基线。
2. **工程收敛**：建立包结构和单 CLI；清理依赖；统一配置、路径、日志和文件对话框；此阶段继续保留 PyQt5，减少同时变化面。
3. **模块化**：抽出 request/result/event、pipeline、engine、writer、worker；用现有 GUI 接入新 Service，并以回归测试确认输出不变。
4. **换 UI/架构**：Service 稳定后再决定 PySide6、PyWebView、FastAPI 或 Tauri。仅本地桌面且追求 Web 视觉时优先 PyWebView；需要浏览器访问/远程调用时再选 FastAPI；不建议当前直接引入微服务。

## 明确不建议的顺序

- 不要先把 PyQt5 全量改成 PySide6 再解耦；那只是框架迁移，会把 955 行主类原样搬家。
- 不要同时重写 UI、核心管线和依赖环境；发生转录质量回归时难以定位。
- 不要把模型直接常驻 GUI 主进程；GPU/OOM/底层库故障会带崩界面，取消和重启也更难处理。
- 不要在没有样例与 golden output 测试时重写文本后处理逻辑。
