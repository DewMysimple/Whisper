# 后续 UI 修改单批次标准流程

建立日期：2026-07-18。

适用范围：用户在 `C:\Users\Administrator\Desktop\WhisperUI` 完成新一轮第三阶段 UI 修改后，授权把该代码成果更新到 `F:\WhisperSubtitle` 正式 Tauri/React 软件。

## 1. 用户如何授权

用户无需重新描述第四阶段全部规则。以下语句或语义等价的明确指令，即授权执行一次完整回迁批次：

> 我已经在第三阶段工程再一次修改了 UI，你需要严格依据第三阶段工程的代码更新软件的 UI。

收到授权后，Agent 默认直接执行，不再要求用户分别批准快照、页面、测试和封版检查点。

## 2. 一个授权只形成一次修改记录

- 默认一次授权、一个代码快照、一次完整执行、一份 `第n次修改.md`。
- 单次执行覆盖本轮全部指定 UI 差异、正式状态映射、测试、Tauri 构建和日志。
- 内部检查点只用于风险隔离和进度控制，不增加用户授权次数。
- 同一次修改中发现普通 UI 偏差时应继续修正，不把每个偏差变成新批次。

建议命名：

- 代码快照：`UI-YYYY-MM-DD-RNN`。
- 修改日志：`后续UI修改日志/第n次修改.md`。
- 第一次 UI 修改已经归档，第 2、3、4、5、6、7、8 次修改已经完成；下一次实际 UI 或 UI 功能修改使用 `第9次修改.md`。

## 3. 内部检查点

### 检查点 A：只读保护与代码冻结

- 读取第三、第四阶段交接资料和上一轮报告。
- 记录两个 Git 工作区状态、正式工程受保护文件和既有修改。
- 对第三阶段模块化源码、资产、构建脚本和必要日志生成 SHA-256 清单。
- 不运行会改写第三阶段产物的构建脚本，除非用户同时授权修改/调和第三阶段或明确要求重建预览。

### 检查点 B：HTML/React 结构差异

- 逐页读取 `src/pages/*.html` 和 `src/components/*.html`。
- 为每页列出必须存在、必须不存在、需要正式状态适配的区域。
- 逐项摘录可见文字、单位、时间范围、状态名称、帮助说明和无障碍标签。
- 对照正式 React 组件确定新增、修改、移动和删除的 UI。
- 功能必须保留，但不得因为原组件存在就保留快照未包含的页面区域。
- 每项差异必须归入精确回迁、真实数据映射、纯演示排除或功能冲突待决。

### 检查点 C：CSS 代码与级联顺序

- 先读取 `build-preview.ps1` 的 `$styleModules`，只把实际加载的 CSS 视为当前视觉事实；不得根据历史文件名假定其仍生效。
- 当前 R02 基线加载 `formal-ui-baseline.css` 和 `prototype-adapter.css`；以后若构建顺序变化，必须以当轮脚本为准。
- 登记精确 Token、字号、尺寸、行列数量、圆角、间距和响应式规则。
- 对同名选择器确认最后生效的代码值。

### 检查点 D：正式状态映射

- 视觉结构映射到 React 组件。
- 交互映射到现有 Zustand 与 DesktopBridge。
- 原型模拟 Worker、任务、性能、路径、输出和 Toast 不得进入正式状态。
- 正式契约不提供的字段不伪造。
- 发现设计语义与真实数据机制冲突时暂停该项并向用户报告；不得自行改文案或用不真实的数据迎合文案。

### 检查点 E：代码级验收

- DOM/E2E 验证页面区域必须存在或不得存在。
- 断言第三阶段规定的可见文字、单位、时间范围和状态，并断言不得出现未经批准的替代文字。
- 对网格行列数、列表数量和关键结构进行精确断言。
- 使用 `getComputedStyle` 验证字号、尺寸和关键 Token。
- 验证功能所在页面、真实状态来源和键盘/无障碍行为。
- 对时间范围和状态文字同时验证实际数据窗口，不能只验证页面上写了什么。
- 截图只检查溢出、遮挡、裁切和整体布局。

### 检查点 F：正式工程验证

- 前端格式、Lint、类型检查、单元测试和 E2E。
- 依据改动范围决定是否复跑 Python 与 Rust；未运行必须记录原因。
- 构建 Tauri Release EXE，并执行受控启动烟测。
- 不发布、不安装、不提交 Git。

### 检查点 G：差异审计与封版

- 确认第三阶段工作区未被越权修改；若用户明确授权反向调和，则改为确认所有写入均在授权范围并冻结新快照。
- 确认 Python、IPC、Preset、任务和输出契约未被 UI 回迁改变。
- 确认受保护文件和用户既有修改未被覆盖。
- 写入一份 `后续UI修改日志/第n次修改.md` 并更新本 README 的修改索引。

## 4. 何时必须先提示分批

默认不分批。只有出现可具体证明的高风险时，Agent 才在正式代码写入前暂停并建议拆分，例如：

- UI 变化实际要求修改正式协议或业务语义。
- 第三阶段代码自身存在互相冲突的结构或 CSS 级联。
- 用户既有修改与本轮目标无法安全隔离。
- 必须同时重构正式状态架构，无法增量映射。
- 关键规格无法建立可靠的代码级测试。

提示必须给出风险证据和最小拆分方案，不能只因为工作量大就要求分批。

## 5. 第 n 次修改日志必填项

1. 用户授权原文。
2. 代码快照名称、清单摘要和第三阶段状态。
3. HTML/React 页面结构差异。
4. CSS 模块、加载顺序和精确规格差异。
5. 可见文字、单位、时间范围、状态与无障碍语义差异。
6. 四类差异账本及用户对冲突项的决定。
7. 正式组件及状态映射。
8. 明确排除的模拟数据和演示行为。
9. Python、IPC、Preset、任务和输出契约结论。
10. 代码级测试、构建和桌面烟测结果。
11. Git 工作区及受保护文件审计。
12. 遗留偏差、验收状态和下一轮触发条件。

## 6. 阶段并行关系保持不变

- 第三阶段继续独立修改 UI。
- 第四阶段不会自动同步第三阶段变化。
- 每次用户授权都冻结一个新的代码快照，执行一次完整修改，并生成一份新的 `第n次修改.md`。
- 上一轮正式实现不会因第三阶段出现新版本而自动失效。
- 第四阶段发现设计问题只记录，不反向修改第三阶段工程，除非用户明确授权返回第三阶段。
- 用户明确要求以正式 UI 为基准反向抽离时，允许在同一次授权内同步第三阶段，但必须登记调和方向、演示排除项和新快照；完成后仍恢复非自动同步。
