# 待办：窗口最小尺寸与屏幕兼容性

记录日期：2026-07-18。

状态：`Deferred / 1950 × 1330 Rejected`。

记录性质：响应式尺寸分析、被取消的配置方案和未来决策依据。当前没有实际 UI 修改，不占用“后续 UI 修改日志”编号；下一次实际 UI 修改仍应使用 `第2次修改.md`。

## 1. 用户目标

用户希望找到一个窗口最小尺寸，使正式软件中的卡片组件不会因响应式规则而改变列数、顺序或堆叠方式。

本次分析把“卡片不调动”区分为两个层级：

1. 卡片不换列、不堆叠：保持各页面主要卡片的桌面排列结构。
2. 完全不进入任何紧凑断点：除卡片结构不变外，侧栏宽度和工作区比例也不发生断点切换。

## 2. 代码与 DOM 测量结果

测量依据：

- 正式 `apps/web/src/styles.css` 的全部宽度媒体查询。
- 第三阶段 `C:\Users\Administrator\Desktop\WhisperUI\src\styles` 中的响应式规则。
- 使用 Playwright/Edge 在工作台、任务记录、性能监控和偏好设置页面读取 DOM 与 `getComputedStyle`；没有依赖截图估算。

关键结果：

| CSS 内容视口宽度 | 实际布局行为 |
| ---: | --- |
| `1261px` | 完整 348px 侧栏；工作台保持双列；任务摘要四列；性能下半区双列、详情三列；设置双列 |
| `1260px` | 命中紧凑断点，侧栏从 348px 改为 320px，工作区卡片宽度重新分配，但主要卡片尚未堆叠 |
| `1180px` | 仍保持工作台双列、任务四列、性能详情三列和设置双列，但已处于紧凑侧栏模式 |
| `1100px` | 工作台改为单列；任务摘要四列改两列；性能详情三列改两列 |
| `900px` | 设置和性能下半区等继续改为单列 |

正式和第三阶段 CSS 均没有基于窗口高度改变卡片列数的媒体查询。高度不足时采用纵向滚动，因此高度不是卡片重排断点。

分析结论：

- 只要求主要卡片不堆叠，CSS 临界值是大于 `1100px`；当前 `1180px` 已满足。
- 要求完全不触发 `1260px` 紧凑断点，理论 CSS 最小宽度是 `1261px`。
- 考虑 Windows 窗口边框、WebView2 逻辑尺寸和缩放取整，曾建议未来可评估 `1280 × 720`，但没有获得实施授权。

## 3. 被取消的 1950 × 1330 方案

用户随后提出把最小宽度固定为 `1950px`、最小高度固定为 `1330px`。

实施前已明确提示以下风险：

> 1950 × 1330 会大于常见的 1920×1080 屏幕，程序在这类屏幕上无法缩小到完整可见范围，底部或右侧可能超出屏幕。

该风险还会影响：

- 1920×1080 及更低分辨率显示器。
- Windows 任务栏占用后的实际工作区。
- 125%、150% 等 DPI 缩放下的逻辑可用区域。
- 笔记本屏幕、远程桌面和多显示器中较小的副屏。
- 标题栏、关闭按钮或页面底部操作区域的可访问性。

用户基于上述影响明确取消执行，并要求只保留工作日志。

## 4. 短暂修改与完整恢复说明

收到最初执行指令后，正式 `tauri.conf.json` 曾在构建前短暂改为：

- 默认启动尺寸 `1950 × 1330`。
- 最小窗口尺寸 `1950 × 1330`。

用户取消后已立即恢复为原正式配置：

```json
"width": 1440,
"height": 900,
"minWidth": 1180,
"minHeight": 720
```

恢复发生在前端构建、Tauri Release 构建和 EXE启动测试之前。因此：

- 没有生成采用 `1950 × 1330` 的正式 EXE。
- 没有改变当前唯一最新桌面程序的运行行为。
- 没有生成安装程序或 `dist\release`。
- 没有修改第三阶段工程。

## 5. 当前决定

- 当前继续使用默认启动尺寸 `1440 × 900`。
- 当前继续使用最小窗口尺寸 `1180 × 720`。
- `1950 × 1330` 明确标记为已取消方案，不得自动恢复。
- `1280 × 720` 只作为未来可能重新讨论的兼容性建议，不是待执行任务。
- 未来如果重新调整窗口最小尺寸，必须先确认目标显示器范围、Windows DPI 缩放和卡片重排定义，再由用户明确授权。
