# HTML 抽离策略与 UI 不同步根因讨论

记录日期：2026-07-18。

## 用户关注

用户采用 `C:\Users\Administrator\Desktop\WhisperUI` 纯 HTML 工程反复调整 UI，再明确授权回迁到 `F:\WhisperSubtitle` 正式 Tauri/React 软件。首次回迁后陆续发现热力图结构、“最近任务”、功能区字号和性能页时间范围等不同步，因此需要判断该策略本身是否可靠。

## 结论

HTML 抽离策略本身可继续使用。它适合快速讨论页面结构、文字、Token、CSS、响应式和演示交互，但第三阶段源码应被定义为“版本化、可执行的 UI 设计契约”，不能只被当作大致参考，也不能机械覆盖正式 React。

不同步的直接原因是迁移纪律和测试门禁不足：

- 页面级映射过粗，没有逐项登记文字、时间、单位、区域不存在性和最终 CSS 数值。
- 实现者根据正式组件或数据机制自行解释设计。
- “正式功能优先”被错误扩张为可以静默改变 UI 语义。
- 测试覆盖了页面、交互和部分尺寸，却没有覆盖所有精确文案和数据含义。
- 截图曾被用于整体近似验收，无法替代源码差异账本。

## 性能页时间范围实例

第三阶段源码明确规定：

- `15s / 7.5s / 现在`。
- “时间范围 15s 至现在”。
- 80 × 20 热力图。

正式软件却使用每 2 秒一次、最多 60 次历史，并显示“60 次前 / 30 / 现在”，约为 120 秒。该偏差不是 HTML 识别失败，而是回迁时未经用户批准，把第三阶段时间语义改成了符合现有状态结构的采样次数语义。

用户随后已明确授权执行。第 3 次修改不是只更换文字，而是以样本时间戳实现真实最近 15 秒窗口，并将轮询目标调整为约 190ms，以 80 列呈现 `15s / 7.5s / 现在`。正式数据仍来自 Desktop bridge/Worker，不使用 HTML 演示常量。

## 已采纳的防不同步机制

1. 每轮冻结第三阶段模块化源码与加载顺序。
2. 建立逐页、逐项差异账本，而不是只写页面已迁移。
3. 所有差异只能归入精确回迁、真实数据映射、纯演示排除、功能冲突待决。
4. 功能冲突必须向用户报告，不得自行重设计或伪造数据。
5. 对文案、时间、单位、区域、网格、字号、尺寸和真实数据来源建立自动断言。
6. 截图只辅助检查溢出、遮挡和整体观感。
7. 未经用户批准的偏离不得进入“完整回迁”声明。
