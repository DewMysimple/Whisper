# 报错处理 003：任务结束通知重复、取消后误报完成与无声

日期：2026-07-20。  
状态：已修复、已完成前端与 Rust 回归、已重建正式桌面 EXE；等待用户执行一次真实任务复验通知次数和实际听感。

## 1. 用户可见现象

第 12 次修改加入任务结束系统通知后，用户实际取消任务时发现：

- “转录任务已取消”通知持续重复循环；
- 取消任务后还会额外出现一次“转录任务已完成”；
- 通知没有声音；
- Windows 通知横幅把发送者显示成 `Windows PowerShell`。

用户截图中的通知正文为：

```text
转录任务已取消
P1-请先看这里.mp4 · 任务已取消
```

本问题是正式 React/Tauri 通知链路错误，不是 Python Worker、Preset、CUDA 或转录结果错误。

## 2. 根因

### 2.1 重复取消与额外完成通知

`apps/web/src/state/workspace.ts` 的 `handleEvent` 在处理 `task.queued` 之后，把其余任务事件统一落入一段终态处理逻辑。该逻辑虽然会正确更新 `task.progress`，但更新完成后没有返回，随后继续执行通知代码。

通知状态使用：

```text
completed -> completed
failed    -> failed
其他      -> cancelled
```

因此每一条 `task.progress` 都被错误解释为一次取消通知。任务真正完成时，合法的 `task.completed` 又会产生一次完成通知，于是形成“循环取消 + 最后完成”的组合。用户看到的现象与该代码路径完全一致。

原实现也没有终态幂等门禁；如果同一任务收到重复终态或“取消后晚到完成”，UI 状态和通知都可能再次变化。

### 2.2 没有声音

原实现只向 Tauri Notification 插件传递 `silent: false`。这只是允许 Windows Toast 使用当前通知声音策略，并不保证未安装的直接 EXE 一定发声。

当前软件按用户约束使用 `tauri build --no-bundle`，没有安装包和正式 Windows AppUserModelID。截图中通知发送者显示为 `Windows PowerShell`，进一步证明当前 Toast 走的是未安装环境兼容路径；该路径的显示身份和提示音均不可靠。

## 3. 修复

### 3.1 任务事件严格分流

`task.progress` 现在单独处理并立即返回：

- 只更新运行状态、进度、阶段、耗时和当前输入；
- 绝不调用结束通知；
- 任务已经结束时，晚到的进度直接忽略。

终态处理增加“第一个终态生效”门禁：

- `completed`、`failed`、`cancelled` 任一状态落地后即视为不可逆；
- 重复终态不再更新、不再通知；
- “取消后晚到完成”保持取消，不再误报完成；
- “完成后晚到取消”同样保持完成。

### 3.2 Windows 原生系统提示音

新增本地 Tauri 命令 `play_notification_sound`，直接调用 Windows `MessageBeep`：

- 完成：`MB_ICONASTERISK`；
- 失败或取消：`MB_ICONEXCLAMATION`。

React 通知层在请求任务栏注意提示后调用该原生命令，再尝试发送 Toast。原生声音与 Toast 权限分离：即使 Toast 权限被拒绝或未安装 EXE 的 Toast 没有声音，仍会请求 Windows 播放系统事件音。

提示音继续遵守 Windows 音量、静音、声音方案和输出设备设置。系统明确禁用声音时，软件不会绕过用户设置强制播放媒体文件。

所有注意提示、声音和 Toast 调用仍是非阻断的；任一调用失败都不会影响任务终态或输出结果。
