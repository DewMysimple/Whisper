## 后续阶段命名规则

- 第三阶段：`30-第三阶段-<主题>/`
- 第四阶段：`40-第四阶段-<主题>/`
- 后续阶段继续使用 `50`、`60`、`70`。
- 每个阶段目录必须包含自己的 `README.md`、范围、批次索引、状态和验收入口。
- `80-历史评估` 与 `90-原始需求` 是参考资料区，不占用阶段编号。

## 事实优先级

当不同资料出现冲突时，按以下顺序判断：

1. 当前 Git 工作区中的代码和自动化测试。
2. `docs/` 下的当前架构文档。
3. `00-项目记忆/当前工程状态.md` 中注明日期的快照。
4. 批次 10 的最终报告。
5. 更早的批次报告、计划和初始评估。

历史报告描述的是生成当时的状态。例如批次 10 报告写有“尚未提交”，但之后这些成果已提交为 `0b3a289`；后续 Agent 不应把旧时间点描述误认为当前状态。

## 保留原则

- `90-原始需求/` 保存用户原始需求，不在整理记录时改写。
- 历史报告、音频、golden、benchmark JSON 和执行记录保留其证据关系。
- `.workbuddy` 是用户工作区数据，不修改、不删除。
- 用户要求删除的内容应移动到 Windows 回收站，不进行永久删除。
- 未经用户明确要求，不自动执行 Git 提交、标签或推送。
