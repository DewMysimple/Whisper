用户计划做三个版本，构成演进式学习路径。核心理论：**V2 把业务逻辑从 UI 剥离成独立 Service 层，是 V3 不白做的关键。**

### V1 — 补缺陷·备份基线

**目标**：把当前 PyQt5 单体版本的缺陷补齐，做到实用，作为学习记录与软件备份保存。

**可行性**：高。补缺陷 = 样式抽 `.qss`、`QSettings` 持久化、`QFileDialog` 换 tkinter、参数单一来源、桌面路径去硬编码、`launcher.py` 退役 VBS。

**理论定位**：规范化收尾，**不是重构**。V1 是独立交付物，建立"确定能用的版本"兜底。

**红线**：只动缺陷和规范，不动架构。保持 PyQt5 单体，能跑、能备份、代码规范即收手。避免做成 V2 的半成品。

### V2 — 解耦重构·模块化

**目标**：模块化管理、技术先进、不复杂、标准先进实用。

**可行性**：中高。核心理论是**关注点分离（Separation of Concerns）**——把 `WhisperMinimalGUI` 拆成三层：
- **UI 层（薄）**：只管显示和操作，不碰引擎。PySide6。
- **Service 层**：封装"加载模型、接收任务、跑转录、回报进度"，不依赖任何 UI，是纯 Python 模块。
- **引擎层**：faster-whisper 原样。

**V2 的真正交付物不是 UI，是 Service 层**——它独立且接口清晰后，V3 只是"给同一个 Service 接个 Web 前端"，而非重写。

**"先进且不复杂"的正确理解**：先进 = 分层清晰 + 职责单一 + 能写单元测试，**不是** = 微服务/依赖注入/设计模式堆砌。最朴素的 view/service/model 三层即可。

**检验标准**："如果 V3 要接 Web UI，我能不能不动 Service 层一行代码就接上？"能，V2 成功；不能，回去重拆。

**风险**：过度设计。学生最容易犯的错。

### V3 — Web UI·审美交互

**目标**：用网页技术做 UI，满足审美和交互需求。

**可行性**：高，但选型决定成败。几条路：

| 路径 | 壳 | 前端 | 后端 | 学习成本 | 评价 |
|------|----|----|------|---------|------|
| **PyWebView** | Python webview | HTML/CSS/JS | Python 单后端 | 低 | ★ 推荐 V3 起点 |
| **FastAPI + 浏览器** | 浏览器 | HTML/JS | FastAPI | 中 | 想学 Web 全栈 |
| **Tauri** | Rust | React/Vue | Python sidecar | 高 | 以后挑战用 |
| **Electron** | Node | React/Vue | Python 子进程 | 中高 | 体积大，不推荐 |

**推荐**：V3 起点用 PyWebView——Python 启动窗口渲染 HTML/CSS/JS，前端通过桥调用 V2 的 Service。保留 Web UI 审美自由（动画、毛玻璃都行），又不用学 Rust/Node，复用 V2。Tauri/Electron 留到想做产品时再上。

### 三个必须守住的理论原则

1. **演进，不是重写**：每版只换一层外壳，引擎层贯穿三版不动。
2. **V2 的 Service 层是 V3 的命**：V2 不解耦，V3 就重写；V2 解耦了，V3 就是 plug-in。
3. **串行，别并行**：学生精力有限，V1 完存档再 V2，再 V3。每版都是独立可交付。

### 待用户拍板的关键问题

1. V3 的"审美和交互诉求"具体是什么（毛玻璃/动画/响应式/深色/拖拽）？决定前端选型与工作量。
2. V2 的 GUI 框架是否趁机 PyQt5→PySide6？
3. 三个版本的总周期（学期项目 vs 长期作品）？
4. 愿意为 V3 学多少前端（纯 HTML/CSS/JS vs React/Vue）？
