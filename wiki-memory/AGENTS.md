# WhisperSubtitle 长期记忆维护协议

`wiki-memory/` 保存项目的长期事实、当前状态、有效决策和工作记录。它用于帮助后续任务快速恢复上下文，但不能替代源码、测试、Git 历史或正式文档。

## 每次任务的读取顺序

1. `当前状态/项目概览.md`
2. `当前状态/系统架构.md`
3. `当前状态/当前约束.md`
4. `当前状态/当前待办.md`
5. 与本次任务直接相关的 active 决策、知识页和已知问题

不要默认读取 `历史归档/`。只有在追溯旧结论、验证原始需求或解释历史兼容行为时才读取。

## 信息分层

- `当前状态/`：必须保持精炼，只描述现在仍成立的项目事实。
- `决策/`：记录仍有效的架构、产品和流程决策；被替代时更新状态并指向新决策。
- `知识/`：沉淀可复用的模块边界、排障经验和开发流程。
- `日志/`：按任务记录目标、变更、验证和遗留事项。完成的日志使用 `status: archived`，但仍保留在日志目录中。
- `历史归档/`：已经失效且仅供追溯的材料。不要在日常任务中修改。

## 事实优先级

发生冲突时，按以下顺序判断：

1. 当前源码、配置和自动化测试
2. 当前状态页与 active 决策
3. 正式工程文档
4. 知识页与工作日志
5. 历史归档

发现记忆与源码不一致时，以已验证的当前工程为准，并在本次任务中同步修正记忆。

## 页面元数据

受管理的 Markdown 页面应包含 YAML front matter：

```yaml
---
title: 页面标题
type: state | decision | knowledge | log | moc
status: active | proposed | deprecated | superseded | archived
kind: feature | ui | bug | discussion | test | maintenance | architecture | process | module | operations
updated: YYYY-MM-DD
importance: low | medium | high
source_logs:
  - 日志/相关日志.md
---
```

- `source_logs` 可为空列表，但必须存在。
- `status: active` 表示内容仍参与当前判断。
- 已完成任务日志使用 `status: archived`；不要把普通完成日志移动到历史归档。
- 修改当前事实时，应把本次工作日志加入相关页面的 `source_logs`。

## 写入原则

- 只记录能帮助后续维护的事实、约束、决策和验证结果，不复制大段源码。
- 当前状态页应及时删除失效描述，避免简单追加造成相互矛盾。
- 不直接修改已经归档的工作日志正文；需要纠正时，新建日志并在相关当前页说明。
- 不把临时终端输出、个人机器路径、密钥或大型生成物写入记忆库。
- 一项事实只设一个主要落点，其他页面用链接引用，避免多处维护同一份清单。

## 实质任务完成后的同步步骤

1. 新建或补全本次工作日志，记录目标、实际变更、验证结果、保留项和遗留项。
2. 更新受影响的当前状态、active 决策和知识页，并清理已失效内容。
3. 运行 `python wiki-memory/工具/memory_lint.py index` 更新自动索引。
4. 运行 `python wiki-memory/工具/memory_lint.py check`，确保链接、元数据和索引均通过。
5. 将记忆变更与代码变更放入同一个 Git 提交并推送。

仅查看、解释或完全没有改变工程事实的任务，可以不新增日志。

## 常用维护任务

- 记忆检索：按读取顺序恢复上下文，再通过链接定向深入。
- 记忆同步：更新日志与相关 active 页面，然后重建索引。
- 记忆体检：运行 `memory_lint.py check`，并人工检查当前状态是否包含过期事实。
- 记忆索引：运行 `memory_lint.py index`，不要手工维护自动生成区块。
