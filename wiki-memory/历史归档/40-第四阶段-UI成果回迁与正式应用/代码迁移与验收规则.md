# 第四阶段 UI 代码迁移与验收规则

建立日期：2026-07-18。

建立原因：批次 2 验收发现热力图结构、工作台额外区域和字体模块遗漏。后续回迁必须以第三阶段源码为主依据，截图只允许作为辅助结果检查。

2026-07-18 补充：又发现第三阶段性能页明确规定 `15s / 7.5s / 现在`，正式实现却改成“60 次前 / 30 / 现在”。因此本规则新增可见语义、四类差异账本和冲突暂停门禁。该偏差已在第 3 次修改按真实时间戳整改，并完成一次用户授权的正式 UI 反向抽离。完整说明见[跨阶段 UI 契约与防不同步门禁](跨阶段UI契约与防不同步门禁.md)。

## 1. 事实来源优先级

针对用户明确指定的 UI 快照，视觉事实按以下顺序读取：

1. `src/pages/*.html`：页面结构、区域存在与不存在、语义顺序。
2. `src/components/*.html`：应用外壳和共享组件结构。
3. `build-preview.ps1`：实际 CSS/JavaScript 模块清单和级联顺序，是判断哪些样式文件生效的唯一入口。
4. `$styleModules` 实际列出的 CSS：按脚本顺序读取最终 Token、基础规则和后加载覆盖。R02 当前为 `formal-ui-baseline.css` → `prototype-adapter.css`。
5. 未列入 `$styleModules` 的 CSS：只作为历史资料，不得误当作当前预览事实。
6. `src/scripts/*.js`：只用于理解演示交互，不能作为正式状态或数据实现。

生成的 `index.html` 和 `dist` 只用于核对上述模块的组合结果，不替代模块化源码。

## 2. 正式功能映射规则

- HTML 中存在的视觉区域必须映射到正式 React 组件。
- HTML 中不存在的区域不得因正式工程原先存在而继续留在同一页面；应判断其功能是否需要移至快照指定页面。
- 原型模拟数据不得迁入；正式组件必须读取 Zustand/bridge/IPC 的真实状态。
- 正式契约不提供的数据字段不得伪造；可以保留相同视觉结构并显示正式字段或明确缺省状态。
- Preset、任务、输出、Worker、IPC 和 Python 行为优先使用正式工程实现。
- 可见文字、时间范围、单位、状态名称、帮助说明和无障碍标签与结构、样式同样属于 UI 契约，不能因正式工程原有实现不同而静默替换。
- “正式功能优先”只禁止破坏真实契约和伪造数据，不授权重新设计 UI。发现第三阶段语义与正式数据机制冲突时，必须暂停冲突项、记录证据并向用户报告。

每一项差异必须归入“精确回迁、真实数据映射、纯演示排除、功能冲突待决”之一；不得留下未归类偏差。

## 3. 强制代码级验收

每轮回迁至少完成：

1. HTML 区域清单：逐页记录必须存在和必须不存在的区域。
2. CSS 模块清单：按 `build-preview.ps1` 顺序确认每个模块已迁入或明确排除。
3. 可见语义清单：逐项登记文字、单位、时间范围、状态名、帮助说明和无障碍标签。
4. 精确结构断言：对行列数、DOM 数量和页面区域存在性建立 E2E。
5. 计算样式断言：对用户明确指定的字号、尺寸和关键 Token 读取 `getComputedStyle` 验证。
6. 功能位置断言：功能保留不等于原位置保留；必须同时验证功能所在页面。
7. 正式状态断言：确保显示值来自正式状态而非原型常量。
8. 语义一致性断言：时间范围、单位和状态文字必须与实际数据窗口和正式状态一致。
9. React、Python、Rust 和 Tauri 验证按改动风险执行。

截图只用于发现溢出、遮挡和整体布局问题，不得作为结构、字号、行列数或功能位置的唯一验收证据。

## 4. 完成声明门禁

只有同时满足以下条件才能声明“完整回迁”：

- 页面结构代码清单已逐项通过。
- CSS 模块与级联顺序已逐项通过。
- 明确的数值规格具有代码级断言。
- 可见文字和数据语义具有代码级断言。
- 原型演示状态已经排除。
- 功能冲突已经获得用户决定，不存在 Agent 自行改变的设计语义。
- 正式功能契约测试通过。
- 指定快照、差异和排除项已经写入本轮日志。

第三阶段之后产生的新代码仍不会自动同步，必须由用户指定新快照或差异后重新执行本规则。

## 5. 默认单批次模型

后续每次用户授权同步第三阶段最新 UI，默认只建立一个第四阶段回迁批次。

单批次内部必须自行设置以下检查点：

1. 只读保护基线：记录两个工作区状态、正式工程既有修改和受保护文件。
2. UI 代码冻结：为第三阶段当前模块化源码建立路径、大小和 SHA-256 清单。
3. 结构差异：逐页比较 HTML 与正式 React，登记必须存在和必须不存在的区域。
4. 语义差异：逐项登记可见文字、时间范围、单位、状态和无障碍标签。
5. 样式差异：按 `build-preview.ps1` 顺序检查 Token、页面 CSS、覆盖模块和字体模块。
6. 四类归档：把每项差异归入精确回迁、真实数据映射、纯演示排除或功能冲突待决。
7. 正式状态映射：把设计映射到现有 React/Zustand/DesktopBridge，排除模拟值。
8. 代码级验收：执行文案、DOM 数量、区域存在性、计算样式、真实数据和功能位置断言。
9. 工程验证：按风险执行前端、Python、Rust、Tauri 构建和桌面烟测。
10. 差异审计与日志：记录代码快照、修改范围、排除项、冲突决定、测试和工作区状态。

这些是同一授权批次内的内部检查点，不要求用户逐项回复“继续”。只有发现会超出授权边界或存在高风险时才暂停。

## 6. 必须建议拆分批次的条件

存在以下任一具体情况时，Agent 应在写入正式代码前提示用户分批，而不能默认为了赶进一个批次而降低保护：

- 第三阶段变化要求修改 Python 算法、Desktop IPC、Preset、任务或输出契约。
- 第三阶段模块化源码与 `build-preview.ps1` 生成顺序相互矛盾，无法确定代码事实。
- 正式工程既有本地修改与回迁目标大面积重叠，无法可靠隔离用户改动。
- 同时需要重构正式状态架构和迁移视觉，无法通过现有组件增量映射。
- 无法为关键结构或数值规格建立可靠代码级验收。
- 单次失败将难以定位或无法安全回退到明确检查点。

提示时必须写明具体风险、建议拆分方式和每个批次的验收边界。最终是否分批由用户决定。

页面多、CSS 文件多、测试耗时长或工作量大本身不构成拆批理由。

## 7. 授权语句及授权边界

用户给出类似以下语句即构成一次回迁批次授权：

> 我已经在第三阶段工程再一次修改了 UI，你需要严格依据第三阶段工程的代码更新软件的 UI。

该授权包括：

- 只读检查并冻结第三阶段当前代码状态。
- 修改正式工程中的 UI、对应测试和第四阶段日志。
- 执行本地格式检查、测试、构建和桌面启动烟测。
- 在同一批次内完成必要的验收修正。

该授权通常不包括：

- 修改 `C:\Users\Administrator\Desktop\WhisperUI`。
- 修改 Python、IPC、Preset、任务和输出契约。
- 迁入模拟数据或浏览器产品逻辑。
- Git 暂存、提交、分支、标签、推送或发布。
- 安装包发布或对外分发。

如果用户在同一指令中明确要求“以正式软件 UI 为基准反向抽离到第三阶段”，则仅第三阶段 UI 源码、预览和阶段日志的调和写入被额外授权；Python、IPC、Preset、任务、输出、Git 和发布边界仍不扩大。
