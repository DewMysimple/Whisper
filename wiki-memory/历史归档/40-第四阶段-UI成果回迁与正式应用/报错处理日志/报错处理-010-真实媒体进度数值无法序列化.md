# 报错处理 010：真实媒体进度数值无法序列化

日期：2026-07-25。  
状态：已修复、已补回归并更新正式 Worker。

## 现象

第 25 次修改的真实 CUDA SRT 验收中，模型已成功加载并完成首个片段识别，但当前媒体随后被标记失败，任务终态为 `success_count=0, failure_count=1`。

Worker stderr：

`ProtocolValidationError: data.media_progress_percent is not JSON serializable`

## 根因

真实 faster-whisper 的媒体时长可能是 NumPy 数值标量。计算所得进度百分比虽然可以比较和格式化，但 `round()` 后仍可能保留第三方标量类型。Desktop IPC v1 的严格 JSON 冻结层只接受原生 JSON 数字，因此在发出 `task.progress` 时拒绝该值。

这不是模型、Preset、CUDA、字幕排版或输出写入错误；失败发生在真实进度事件的序列化边界。

## 修复

Worker `_emit_progress` 在进入 IPC 消息前，把：

- `media_progress_percent`
- `media_elapsed_seconds`

显式转换为 Python 原生 `float`，再执行既有的小数位舍入。百分比、耗时和转录算法语义不变。

## 回归

- 新增第三方数值标量归一测试，确认 EventMessage 中两项均为原生 `float`。
- 相关 Python 93 项针对性测试通过；完整 Python 299 项通过。
- 重建冻结 Worker 后，四个 SRT Preset 均以真实 CUDA/FP16 完成，未再出现序列化失败。
- 正式 Worker SHA-256：`99FD1922A7FE5263FDC1C30850690DF5538FC5F54CA51635D980837BCCB48267`。

## 边界

未放宽 Desktop IPC v1 的严格 JSON 校验，未修改推理、Preset、CUDA、时间轴或输出内容，只在 Worker IPC 边界规范化数值类型。
