# NVML 会话资源累积根因与修复

## 继续排查的原因

前一轮已证明退出线程停在 NVIDIA 驱动进程退出回调，并修复 Host 无界等待，但仅修 Host 不能证明已避免整机卡顿。本轮继续寻找可在工程内消除的资源累积，保留原目标，不把窗口能退出当作整机问题已经解决。

用户确认最近没有升级显卡驱动；本机 616.92 安装文件时间为 9 月，系统当天已启动。因此 NVIDIA 关于刚跨分支升级而未重启的说明不能作为本机直接归因。HAGS 配置已禁用，不改系统设置或驱动。曾核验官方 Studio 617.42 候选包签名，但没有安装，发现工程内可验证因素后已删除未用安装包。

只读、脱敏读取桌面任务元数据：当天两条任务均为 Qwen 1.7B／cn2、CUDA 0／bfloat16／CPU threads 0、单 Markdown，媒体分别约 22 分 36 秒和 24 分 16 秒，任务耗时约 110 秒与 117 秒。两任务间隔超过默认 15 分钟模型空闲释放时间，短夹具立即关闭不足以覆盖这个使用模式。没有修改真实 profile、媒体或原输出。

## 可重复的工程因素

bridge 在所有页面约每 190 ms 采集性能数据。原 `collect_performance_sample` 每轮执行 NVML 初始化、所有读取、关闭，约每小时 1.9 万次初始化／关闭。API 允许配对重复调用，不能仅因调用频繁断言非法；本轮通过真实内核资源计数验证其效果。

在同一机器、没有 ASR 工作负载时，各独立进程执行 300 次、190 ms 间隔的 A/B/C 对照：

- A：禁用 NVML，只读同一 CPU／内存 getter。
- B：原采样函数，每次成对初始化／关闭。
- C：保留一个 NVML 会话，其余读取复用完全相同的生产 getter。

B 在约 51 秒稳定区间内，NVIDIA `NVRM` 分页 live 对象增加 267 个，非分页 live 对象增加 8,271 个、非分页池增加约 2.53 MiB，拟合约 50,472 B/s。A、C 的资源基本稳定，C 非分页池斜率约 -10.7 B/s。B 的这些资源到进程退出后才释放，因此只对比退出前后最终归零会漏掉长期运行中的问题。B 单次采样中位约 25.56 ms，C 约 4.95 ms。

这证明本机驱动下原高频会话生命周期会累积进程存续期间的驱动资源，与退出回调需要回收大量资源相吻合；并未宣称已经精确识别 NVIDIA 私有函数中的具体死循环条件。

## 修复

- `NvmlSession` 显式拥有一次懒初始化的 NVML 引用，串行保护读取与关闭；关闭为终态、幂等，初始化失败不在每个采样周期重试。
- 默认 Worker 拥有 `PerformanceMonitor`，连续采样复用同一 NVML 会话和原 getter；dispatcher 停止、模型释放后统一关闭，模型清理异常也会释放监控会话。
- 外部注入 sampler 的生命周期仍由调用方拥有，不擅自关闭。保留一次性 `collect_performance_sample` 入口及其签名供独立快照使用。
- 没有全局隐式单例、atexit、CUDA context reset、驱动更改、UI 采样频率或 IPC／Preset／输出变更。
- 新增显式 `tests/benchmark/run_nvml_lifecycle_validation.py`，观察运行期间内核池斜率并核对真正进程 HANDLE；旧方式压力测试需显式选择且限制次数，异常停止后续用例。

- 最终全量 Python **542 项及 2 个 subtest** 通过；`corepack pnpm check` 通过，Web 173 项。仓库卫生、记忆索引／体检与实际 diff 门禁一并完成。
- 真实生产 `PerformanceMonitor` 连续 3,000 次、50 ms 间隔采样：NVRM 分页 live 对象首尾相同，非分页池首尾仅 +1,184 B、斜率约 -0.18 B/s，未再出现随采样次数的线性积累，真实进程退出通过。
- 旧正式版补真实 GUI 转录验收：两分钟音频完成后保持遥测 143.6 秒，0.899 秒内 Host／Worker 真正退出；它补齐前一轮 GUI 未实际转录的验收范围，但不能代替新修复的正式产物验收。
- 原两段真实长媒体源码复放通过：连续 2,856 次遥测、两次加载与两次 Timer 空闲释放后，两个运行阶段 NVRM 非分页池斜率约 0.57／0.94 B/s、全程约 2,416 B 波动，分页 live 对象保持 266，两个 idle 阶段回到同一固定基线。Worker 与 venv launcher 双句柄在 0.8672 秒内结束，无残留。诊断将源码 idle timeout 缩短为 1 秒以覆盖 Timer 线程释放，未改变正式默认 15 分钟。

- 真实媒体直接对照再次验证根因：旧版运行时 NVRM 分页对象约 +5.07 个/s、非分页池约 +50,412 B/s，模型卸载后仍约 +50,493 B/s；新冻结运行时约 -2 B/s，idle 区间没有上述增长。资源增长来自持续监控会话生命周期，而非模型权重正常占用。
- 新冻结六项退出矩阵全部通过：Turbo、Qwen 0.6B／1.7B 各 command／EOF，每项任务前后均请求真实 metrics，确实激活默认监控器；退出约 0.61–1.41 秒，全部真实 HANDLE 结束、无残留。Whisper golden 与 Qwen SRT 输出复核通过。

## 验证期间的工具纠偏

- Windows venv 的 `python.exe` 可能是启动器，真实 Worker PID 不同；正式 NVML 工具和长媒体 replay 都保留实际 Worker／启动器双 HANDLE，验证身份后才允许采样，失败仅清理自己的进程并保留残留诊断。正式工具补真实无 GPU 正常／超时联调及轻量门禁，避免退出码 0 或启动器结束掩盖内核回收未结束。
- 为并行验收而隔离复制的冻结运行时曾放入忽略的 benchmark 输出目录，导致全量 pytest 误收集其中 Torch 自带测试。验收后移除该可再生运行时副本，再运行全量 pytest 得到上述 542 通过；没有通过修改生产测试或放宽门禁绕过问题。
- GUI 诊断中 PowerShell `Get-Content` 字符串的扩展元数据曾导致 JSON 遍历膨胀；改用纯字符串／标量和 `ReadAllText` 后正常。此问题属于验收脚本，没有当作应用回归或修改正式 UI。

原始对照数据、任务后 GUI 证据及脱敏 replay 报告留在忽略目录 `tests/benchmark/runs/2026-11-02-shutdown-followup/`。不提交真实用户媒体、原始路径、正文或大型诊断。

本轮修复的是应用持续监控引起的资源累积与其退出风险，不声称修改了 NVIDIA 私有驱动实现或证明所有驱动异常永远不会发生。没有重启、安装显卡驱动、修改 HAGS、变更模型／硬件偏好或识别输出。原媒体、原输出、真实 profile、模型、开发环境、Node 依赖和 `prompt/` 均保留。

## 收尾

按约定先运行 `workspace:clean` 预览，再运行 `workspace:finish`，均成功；清理前再次全量核对标准便携版 5,947 项文件。移除构建、Rust target、测试缓存、自己创建的 WebView profile 和用于并行验收的可再生冻结运行时副本。保留原始内核追踪、必要的资源曲线／脱敏报告和隔离输出，不清理任何用户原始媒体或输出。清理后只做不生成字节码的记忆／Git 收尾，不重跑会生成缓存的检查。

`workspace:size` 最终记录 **27.81 GiB**（29,866,107,557 字节、50,317 文件）：dist 13.57 GiB、模型 8.51 GiB、开发环境 5.45 GiB、Node 依赖 0.18 GiB，测试目录约 0.09 GiB（包含本轮保留的诊断证据）。日常仅保留标准便携版及校验文件，无候选发布目录或 ZIP。
